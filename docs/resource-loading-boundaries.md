# 資源の読み込みとキャッシュの責務

## 原則

読み込み・保持・変更検知・再利用・破棄の仕組みは、ファイル形式に依存させない。
文字列、画像、DOM、図形などへの変換と、それぞれの更新条件は利用する側で扱う。
共通化の採用は、既存の動作・安全条件・描画精度・実測性能を維持できた時点で判断する。

## 境界

| 責務 | 担当 | 境界に入れないもの |
| --- | --- | --- |
| 元文書の取得、スクロールバーの描画 | KRRを呼び出す利用側、CLI | KRR内部の解析済み状態 |
| 生バイトの取得、共有する資源の所有と識別 | 形式に依存しない共通処理 | Mermaid等の種類、UTF-8、DOM、画像形式 |
| 同梱資源の展開、配置、配布物の検証 | 既存のruntime assets処理 | 文書セッション、HTTPのアクセス可否 |
| UTF-8変換、BOM、画像判定、JavaScriptの実行 | 各形式のアダプタ | 形式ごとの別のファイルキャッシュ機構 |
| URL解決、origin、通信、資源サイズ制限 | HTMLの取得アダプタ | アクセス制限を省いた共通キャッシュ参照 |
| 解析済みDOM、実行中JavaScript、layout | 文書・描画セッション | プロセス全体への無制限な保持 |

アクセス制限を判定してから取得・再利用する。共通キャッシュが別文書の権限を引き継がないようにする。
表示幅やテーマなど解析後の結果へ影響する条件は、該当結果の識別と無効化に含める。
読み込み済み資源を保持することと、DOMやJavaScript状態を保持することは別々に検証する。
外部ライブラリが所有する読み込み・解析・内部キャッシュは、その公開APIへ委譲する。
KRR側に同じ機構を重ねず、KRRが所有する取得経路の共通化と区別する。

## 保持と変更の契約

- 不変の同梱資源は、既存の展開済みデータを共有し、呼出しごとの読み直し・複製を避ける。
- 明示した外部ファイルは、同じパスの書換え・置換・削除を反映する。
- 読み込んだ内容と、その描画・キャッシュ識別に使用する内容を同じ取得結果に結び付ける。
- 外部ファイルは毎回openし、サイズ・更新/作成時刻と、利用可能な物理同一性・変更情報から通常の書換え・置換を検知する。読込中の変化も確認する。更新時刻とサイズだけに依存せず、属性の意図的な偽装を完全検出するという条件は新設しない。
- 任意のパスやURLを、容量上限も寿命もないグローバルな領域へ蓄積しない。
- HTTP応答の再利用条件を、ローカルファイルや同梱資源の条件から推測しない。
- 既存ライブラリで保持・容量制御を実現できる場合は優先して評価し、同じ機構を独自に作らない。

今回の候補は[Mokaの同期キャッシュ](https://docs.rs/moka/latest/moka/sync/struct.Cache.html)を使用し、保持・追い出しのアルゴリズムを委譲する。
重みは資源本体・パス・管理分を含め、設定は16MiB、超過する単一資源は保持しない。
Mokaの容量管理はbest effortであり、利用側が取得済みの共有データを保持する期間のメモリは別に残る。
この設定値だけでメモリ非劣化や厳密なRSS上限を証明したとは扱わず、実測する。
SHA-256は不変snapshotに対する要求時の一度だけ計算し、HTMLのバイト取得だけには不要な計算を追加しない。

## 検証

共通機構は文字列とバイナリの両方で検証し、書換え・置換・削除・エラー伝播を確認する。
各アダプタでは、既存の文字コード・アクセス制限・サイズ制限・実行順序を維持する。
resize等の文書内操作では、資源の再利用とDOM・JavaScript状態の維持を個別に確認する。
重複検査には製品とテストの双方を含め、テスト準備の重複も共通化する。
性能は初回表示・再表示・resizeを区別し、利用中の従来APIでも秒数とメモリを測定する。
ソースの移動、キャッシュの存在、検査成功だけで性能改善とは判定しない。

誤った例は、JS専用の文字列ローダーだけを共通化して資源全体の共通化を完了扱いすること。
正しくは、共通の取得・保持境界と各形式の変換・状態管理を、実際の呼出し経路と回帰で確認する。

検索語: `resource loading boundary`, `format-independent bytes`, `cache ownership`, `same snapshot`, `reuse invalidation`。
