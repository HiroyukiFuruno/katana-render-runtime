# HTML性能の測定履歴

測定結果の履歴と比較に使う現行基準は [html-performance-history.json](html-performance-history.json) で管理する。`records`は不変の測定履歴、`activeReferenceRecordId`は現行比較基準の選択を表す。再計測や進捗回答の前に両方を参照する。

閲覧には `just html-performance-history` を使う。特定recordは `just html-performance-history html84-ea855b56-r6628` のように指定できる。表示される履歴値は過去測定であり、現HEADの受入を意味しない。

## 記録済みの結果

`html84-ea855b56-r6628` はコミット `ea855b56b4c6733d3617e74da58133f4a10e68a8` の実測結果で、R6628の正式検証は終了コード0。候補84条件を各25回、6段階で測定した。旧版と比較できた72条件は表示速度とメモリの非劣化、旧版が失敗する12条件は候補の正常動作と表示3秒未満で判定した。

| 段階 | 候補の最長表示時間（秒） |
| --- | ---: |
| 初回表示 | 0.104136167 |
| 再表示 | 0.043863833 |
| 同一セッションのresize | 0.036037041 |

JSONには全6段階の時間・ピークRSS・試行数・測定元コミット・入力束の識別値・正式検証結果・元データのSHA256を保存する。時間の単位は秒、RSSはbyte。中央値と95パーセンタイルは候補84条件の標本をまとめた集計で、処理不要の条件も含む。個々の条件の性能判定は元の正式検証に従う。

この履歴は測定時の結果であり、現行版やリリース全体の合格を自動的に意味しない。測定元コミットと、元の入力・計測条件を束縛するbundleのSHA256を一緒に参照する。

現行基準はJSONの`activeReferenceRecordId`で確認する。性能改善が同一の正式条件で実測され、全対象の受入条件を満たした場合は、新しい測定recordを追加したうえで選択を更新する。旧recordと測定値は履歴として残し、Git履歴で変更を追跡する。同等の結果や測定揺らぎでは基準を更新しない。候補84条件すべての各フレーム表示は3秒未満とし、比較可能な全条件の時間非劣化と、以下の版別メモリ条件を維持する。

## 一時的なピークと解放後の保持量

2026-11-07のユーザー指示により、新規公開と基準昇格には`html-memory-v2`の全84条件を必須とする。旧v1のピークRSS判定・履歴・原本は当時の結果として保持する。

v2の初期設定は、一時ピークの中央値・p95・最大値の増加が各1MiB以内かつ5%以内なら、時間非劣化を維持して許容する。それを超える増加は8MiB以内かつ25%以内に限り、同じphaseの25組で速度改善を確認し、中央値で10%以上かつ1ms以上の短縮を要する。別phaseの時間悪化は免除しない。

保持量は同一processで実操作をwarm-up5回・測定25回行い、sessionと結果JSONの解放後のRSSを確認する。初末5点の中央値差が1MiBまたは初期中央値の5%を超える場合、および全窓と末尾10点に上向き傾向が持続する場合は拒否する。傾向は既存SciPyで全84条件の多重比較を補正して評価する。VMSも観測へ保存する。閾値は実装上の初期設定として版付きで管理し、欠測や未認証の観測を合格にしない。

v2の履歴recordには判定と保持量証跡のdigest・条件数・繰り返し回数を追加する。元の測定値を修正せず、新しい正式結果で改善を確認してから参照基準を更新する。

## 再利用と再計測

非 SDK 計測依存を固定 parent と揃えるため、SDK 側を含め `smallvec 1.16.4` を維持する。
`1.16.5` の変更は CI・整形とコメントであり、実行コードや依存宣言に差はない。将来の更新は個別に再評価する。[upstream 差分](https://github.com/smallvec/smallvec/compare/v1.16.4...v1.16.5)

1. 計測前に履歴を調べ、該当する元のclosed bundleと正式検証結果を選ぶ。
2. 同じ実行ファイル、入力・資源・フォント・操作、計測プログラム、ツール・計測環境、判定条件であることを既存の厳格な検証経路で確認する。元の測定結果と、新しい版への再利用適格性を分けて記録する。
3. 文書やテストの変更だけを理由に全84条件を再計測しない。影響する入力が変わった場合は、その範囲を根拠付きで再計測する。影響範囲を確定できない場合は必要な範囲を広げる。
4. 元のreceipt・コミット・入力pinは書き換えない。再利用は独立した適格性の証跡として追加し、履歴の集計値だけを正式測定の代わりにしない。
5. 測定が終わったら新しいrecordを履歴へ追加する。過去recordの測定値は変更せず、正式条件で改善を確認できた場合に限り現行基準の選択を更新する。再利用する実行ファイルと原結果は、既存の保護・整理手順で保持する。

文書変更後の再利用は、`just html-performance-evidence-reuse` で独立した適格性証跡を作成する。許可された文書差分、元の正式bundle、実行ファイル、資源、計測環境等の同一性を検証し、元receiptは変更しない。実データを使う統合検証の完了は、品質ゲート改善台帳で別途確認する。

現在の自動的なsource再利用は許可された文書差分に限る。Rustのテスト変更後の影響範囲を自動証明する機能は未整備であり、テストファイル名だけを理由に性能検査を省略しない。

正式な84条件のpaired比較後は、`just html-performance-evidence-promote <bundleの絶対パス> <新規の非公開証跡ディレクトリ> <run-id>` で基準を更新する。固定Python環境で元結果を再検証し、時間非劣化とv2のメモリ条件を満たし、ばらつきだけでは説明できない改善を確認した場合に限り、新recordを追加して現行基準を切り替える。改善がなければ履歴を保持し、検証失敗や競合時は更新を拒否する。過去recordの参照と新規昇格を区別する。

私有原本、環境変数、認証情報、生の実行観測は管理外に保持する。Gitには確認済みの数値・条件・識別値だけを保存する。

## 測定中のCPU負荷

現在の観測には固定版psutilの`cpu_times_percent`を使い、worker前とworkerを含む区間をそれぞれ1秒以上観測する。過去平均のload averageとは方式を区別する。実機では短い窓でカウンタ未更新の全ゼロが返ることを確認したため、全ゼロをCPUが空いている証拠として採用しない。

CPU時間の内訳・実区間・使用率・方式とソース識別値を保存する。guest時間とWindowsのinterrupt/DPC時間を二重加算せず、使用中psutil版の実装に従って使用率を導く。観測不能のworkerは結果に数えず、保存して上限付きで再実行する。両版を同じ方式で測り、25%の負荷上限、表示3秒未満、時間非劣化と版別メモリ条件を維持する。CPU使用率が低いことだけを性能合格の根拠にはしない。

旧方式の証跡は当時の条件で検証し、新方式との混在やラベルの付け替えを拒否する。部分バッチも保存・再開前にworkerの実行引数と標準出力を対象サンプルへ照合し、正式合格は全84条件が揃った時点で判定する。
